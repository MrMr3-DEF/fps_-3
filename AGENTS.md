# Working on FPS Arena

Start with [docs/README.md](docs/README.md). Read [README.md](README.md) for the project overview and [docs/development.md](docs/development.md) for the contribution workflow and local verification. Use [docs/architecture.md](docs/architecture.md) to find the owning module and lifecycle boundaries, then read the relevant feature guide before editing. [docs/to_be_changed.md](docs/to_be_changed.md) holds requested work; check it against the current code before acting.

- Inspect the working tree before editing. Preserve the existing source-file `.js` import suffixes; TypeScript resolves them to `.ts`.
- Do not modify `AGENTS.md` unless the user explicitly requests it.
- Use the reset helpers in `src/state.ts` rather than carrying player or match state into a new session. `src/config.ts` owns shared gameplay values. Keep the `damage.ts` and `weaponNetworkPort.ts` dependency seams intact.
- Keep match creation, cancellation, reset, and disposal in sync. World generation must remain deterministic for a shared seed; render distance must not change collision or hit authority.
- Treat WebRTC packets as untrusted. A packet change needs a runtime parser, host authority decision, sender/receiver handling, and focused tests. Keep Worker secrets and room capabilities server-side.
- Keep multiplayer fail-closed when security configuration is missing; do not add public STUN/TURN fallbacks. Keep client and Worker TypeScript configurations separate.
- Explain non-obvious invariants and lifecycle reasons in inline comments. Avoid comments that merely restate the next line; update or remove comments when behavior changes.
- Run `npm run check` for source changes. Run `npm run build` for production-affecting changes and include the regenerated, tracked `dist/` output. Do not hand-edit hashed assets.
- Add automated tests only to protect a significant gameplay, security, lifecycle, or reliability requirement, or reproduce a meaningful bug. Identify the concrete failure a new test catches and check existing coverage first. Cosmetic changes, routine refactors, presentation timing, and tuning values normally do not need new tests. Test observable behavior and essential relationships rather than implementation details, duplicated constants, or arbitrary animation samples. Keep setup proportional to the risk; update or remove obsolete tests when intended behavior changes.
- Keep testing and verification to the minimum necessary, including visual inspections. Perform extended testing only when explicitly requested by the user. The required checks and builds above still apply; avoid additional broad checks or repeated successful runs.
- As soon as testing or verification begins, minimize token usage: use focused commands, concise output, and brief result summaries. Inspect detailed logs only when needed to diagnose a failure.
- Documentation describes the current project: structure, architecture, existing features, behavior, module ownership, and code locations. Use short, factual descriptions in the present tense. Do not add dates of past changes, implementation stories, completed-work logs, historical test results, or descriptions of removed features. Update or remove obsolete content instead of appending corrections; Git holds change history. Keep requested work in the explicit follow-up list, separate from descriptions of existing behavior.
- Keep the relevant docs current when behavior or workflows change. For interactive terminal editing, prefer vim over nano.
